# 个人系统方法论

> "你不是在解决问题,你是在设计一个能持续解决这类问题的系统。"

## 为什么需要"成长系统"

- 思考/执行/学习/训练 四大模块各自能跑,但**之间不打通**等于四套孤岛
- 元层面的系统才是"做选择 → 跑一段时间 → 看数据 → 调整" 的闭环
- 不写下来的"系统"会随精力波动;写下来的才稳定可迭代

## 三条设计原则

1. **最小可跑 > 完美设计**
   - 一个能坚持 30 天的烂系统,远胜过一个坚持不下来的完美系统
   - 先把流程跑通(输入 → 处理 → 输出 → 反馈),再优化每一段
2. **数据驱动 > 体感驱动**
   - 每个核心动作尽量留下数字(训练时长、复盘字数、知识卡片数)
   - 季度回看数据,而不是凭"感觉我最近进步了"
3. **可演进 > 一次成型**
   - 系统必须有"复盘 + 改写" 的口子,否则半年后僵化成枷锁
   - 季度做一次大版本号变更(如 v1 → v2),平时只调参数

## 五大子系统如何协同

| 子系统   | 产出物           | 给谁消费                 |
| -------- | ---------------- | ------------------------ |
| 思考体系 | 决策框架 / 复盘  | 执行 → 决策更稳          |
| 执行体系 | 周计划 / 日落地  | 思考 → 不停留在头脑      |
| 学习体系 | 知识卡片 / 笔记  | 思考 + 执行 → 有素材     |
| 训练体系 | 身体状态数据     | 执行 → 精力更好          |
| 成长系统 | 元复盘 / 工具栈  | 上面的四个 → 持续可迭代   |

## 常见误区

- ❌ 把工具当系统 —— 换 Notion / Obsidian 不会让你更系统
- ❌ 把"抄别人的系统"当自己 — 系统必须经过自己磨合才稳定
- ❌ 追求 100% 自动化 —— 关键节点的体感判断比自动化更重要
- ✅ 接受 60% 的稳定度,把精力放在持续优化上
